## UC14: Handle Invalid Bogie Capacity (Custom Exception)

### 🔴 Drawback of UC13 Approach
In UC13, the system focuses on performance comparison, but assumes all data is valid.  
In real railway systems, invalid input can occur such as:
- Negative seat capacity
- Zero capacity bogies
- Corrupted configuration values

If such values are allowed:
- ❌ Passenger allocation becomes meaningless
- ❌ Safety and reporting break down
- ❌ Bugs propagate silently

To prevent this, the system must **fail fast** and stop invalid data at creation time.

---

### 🎯 Goal
Prevent invalid passenger bogies from being created by enforcing capacity rules using a **custom exception**.

---

### 👤 Actor
User

---

### 🔄 Flow
1. User attempts to create a passenger bogie
2. System validates capacity
3. If capacity ≤ 0 → throw `InvalidCapacityException`
4. If valid → bogie is created successfully
5. System continues execution

---

### 🧠 Key Concepts Used
- **Custom Exception** – User-defined exception for invalid capacity
- **Exception Inheritance** – Extending `Exception` class
- **throw Keyword** – Used to raise exception manually
- **throws Declaration** – Declares exception in constructor
- **Fail-Fast Validation** – Stops invalid object creation early
- **Business Rule Enforcement** – Applies domain rules at object level

---

### 📌 Key Requirements
- Create `InvalidCapacityException` class
- Validate capacity inside constructor
- Throw exception if capacity ≤ 0
- Declare constructor with `throws InvalidCapacityException`
- Ensure invalid bogies are never created

---

### ✅ Key Benefits
- Prevents invalid data entry
- Protects system integrity
- Improves reliability
- Encourages defensive programming
- Avoids downstream failures
